# Контракт KAOS-RT

Этот документ определяет границы ответственности ядра, порта и приложения.
Он применяется вместе с публичным API из `fsm.h`.

## KAOS-SRS-001 — Модель исполнения

KAOS-RT предназначен для одного основного контекста исполнения и обработчиков
прерываний одноядерного 32-разрядного микроконтроллера. Ресурсы ядра имеют
фиксированный размер, заданный на этапе компиляции. Ядро не использует
динамическую память.

Автоматы обслуживаются в возрастающем порядке `fsm_id_t`. Меньший ID получает
события раньше в каждом проходе диспетчера.

## KAOS-SRS-002 — Функции автоматов

Callback автомата выполняется до возврата управления диспетчеру. Он должен
делать один ограниченный шаг прикладной работы и завершаться.

В callback нельзя ожидать периферию, DMA, флаг или событие; вызывать задержку,
`WFI`, рекурсию, динамическое выделение памяти, блокирующий журнал или
неограниченный цикл опроса. Длительную операцию следует разделять на шаги и продолжать после нового события.

`fsm_loop_service()` вызывается в начале каждого прохода. Приложение может
предоставить свою реализацию. К ней применяются те же правила, что и к callback
автомата.

## KAOS-SRS-003 — События и IRQ

События одного автомата представлены 32-битной маской. Значения `fsm_event_t`
начинаются с нуля; `FSM_EVENT_COUNT` не превышает 32.

Бит события обозначает ожидающее условие. Повторная постановка того же бита
объединяется. Для передачи отдельных кадров, команд, импульсов и других данных
приложение использует собственный FIFO, счётчик или буфер; `append_event()`
служит уведомлением о готовности данных.

Из IRQ разрешён только `append_event()`. Управление автоматами, событиями и
таймерами выполняется из основного контекста, callback автомата или
`fsm_loop_service()`.

## KAOS-SRS-004 — Жизненный цикл автомата

`set_fsm()` устанавливает callback статического слота и начинает его новый
жизненный цикл: состояние, ожидающие события и таймеры прежнего callback
очищаются. `remove_fsm()` заменяет callback безопасной пустой функцией и
освобождает таймеры слота.

Callback может вызвать `remove_fsm()` для собственного слота. Удаление
окончательно применяется после возврата callback: состояние, ожидающие события
и таймеры слота очищаются. Сам callback продолжает выполняться до возврата.

Callback не должен вызывать `set_fsm()` для собственного слота. Замену
собственного callback выполняет другой автомат или `fsm_loop_service()`.

## KAOS-SRS-005 — Таймеры

Таймер принадлежит автомату и по истечении ставит указанную маску событий.
Одноразовый таймер освобождается после истечения. Периодический таймер сохраняет
свою фазу; несколько пропущенных периодов объединяются в одно ожидающее событие.

Создание таймера требует допустимого ID автомата, ненулевой задержки и ненулевой
маски событий. `FSM_TIMER_COUNT` задаёт число слотов на этапе компиляции.
`fsm_timer_id_t` является непрозрачным дескриптором; устаревший дескриптор не
должен использоваться для управления новым таймером.

## KAOS-SRS-006 — Порт и конфигурация

Порт предоставляет монотонный источник логических тиков, критическую секцию для
согласования IRQ с диспетчером и источник тиков профилирования. Его реализация
учитывает конкретный МК, компилятор и дерево тактирования.

`FSM_TICK_FREQ_HZ`, `FSM_TIMER_COUNT` и флаги диагностики настраиваются до
сборки ядра. Частота аппаратного источника времени задаётся в конфигурации
платы или её сборки, а не в порте: она зависит от конкретного МК и дерева
тактирования. Порт не имеет для неё значения по умолчанию. Имя параметра
зависит от порта, например `FSM_TIMER_CLOCK_HZ` или `FSM_SYSTICK_CLOCK_HZ`.

Порт может предоставлять прикладному коду дополнительную функцию
`port_uptime_usec()`. Она возвращает локальный монотонный uptime в микросекундах
и не зависит от `FSM_TICK_FREQ_HZ` или логических таймеров КАОС. Если
прикладной код преобразует её результат в `int64_t`, он опирается на условие
`port_uptime_usec() <= INT64_MAX`. При разрешении 1 мкс этот предел соответствует примерно 292 тысячам лет непрерывной работы.

Порядок создания нового порта описан в [PORTING.md](PORTING.md).

## KAOS-SRS-007 — Граница ответственности

Ядро обеспечивает описанную модель диспетчеризации. Приложение отвечает за
корректность собственной логики, допустимость объединения событий, размер
буферов, конфигурацию тактирования, обработку отказов и проверку на целевой
платформе.
